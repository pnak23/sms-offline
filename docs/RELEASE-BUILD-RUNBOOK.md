## Part A — taking in the Khmer review (nothing is built in this part)
**Carried out on 2026-11-06 with no corrections:** the owner confirmed the wording acceptable, so the dry run (an empty corrections file) reported 0 changes, `--write` regenerated `km.json` byte for byte (the SHA-256 is the same before and after) and wrote the outcome report. The steps below stay as the procedure for any later review.
1. Give the reviewer `docs/KHMER-REVIEW-SHEET-19-20.md` (or the tables of `REVIEW.md` §19 and §20). Tell them it is AI-drafted, that they should read each text as it appears on the screen, and which ones matter most (the empty-state sentences, the reason given for each skipped lesson, the clash sentence, the word for "timetable"; and on the dashboard the word for "chart", the sentence that a day with no record is a gap and not zero, "ចំណុះ" for capacity, the notice that the grading is not official, the sentence that riel and dollars are never added, and the label of the dashboard's backup information button, "ដែនកំណត់នៃការបម្រុងទុកនេះ").
2. Turn what comes back into a JSON file `{ "<key>": "<corrected text>", ... }` (keys exactly as in the sheet). Texts the reviewer leaves alone are simply not listed.
3. **Dry run:** `node scripts/khmer-review.mjs apply corrections.json`. It prints every change as before / after and every problem, and writes nothing. Fix the file until there is no problem. **Then show the owner every proposed change (the dry run's before / after list) and stop: nothing is written until the owner has said which corrections are approved.**
4. **Apply, only after the owner has approved the proposed changes, and only the corrections the owner approved** (put just those in the file): `node scripts/khmer-review.mjs apply corrections.json --write --reviewer "<the reviewer's name>"`. It changes `frontend/i18n/locales/km.json` and writes `docs/KHMER-REVIEW-OUTCOME-19-20.md`. **Nothing of the review has been applied yet; the reviewer's corrections are applied only after the owner has seen them proposed.**
5. Record the outcome in `frontend/i18n/REVIEW.md` §19 and §20 (who, when, how many texts were corrected, a pointer to the outcome report). **Do not** sign off the readiness item `khmer-wording` for anyone: that is the administrator's act in Settings → About, and §19 and §20 are only part of what that item covers.
6. **Prove that nothing else moved:** `node scripts/release-preflight.mjs --compare` must say *"ONLY the Khmer wording files differ"*.
7. **Re-run what reads the Khmer text:** `npm run typecheck -w frontend`, `npm run test -w frontend`; then, because the screens carry the new texts, `npm run generate -w frontend` and `npm run build -w desktop`, and the real-shell suites that assert them: `npm run e2e:timetable`, `npm run e2e:dashboard`, `npm run e2e:changes`, `npm run e2e:app`, `npm run e2e:shell`. Report every result exactly, with any failure, skip, warning or flaky behaviour.
8. **Show the owner** `docs/KHMER-REVIEW-OUTCOME-19-20.md`, the `--compare` result and the test results. **Stop. Wait for the owner's separate approval.**

## The verification scripts (added 2026-11-06, owner-approved)
Both are Node scripts; run them from the repository root. Prerequisites for both: Windows, Node 24, `npm install` done, the Electron runtime in `node_modules` (`node node_modules/electron/install.js` if `node_modules/electron/dist/electron.exe` is missing), no network. **Neither builds or touches an installer, installs or uninstalls anything, or reads or writes school data.**
| Script | What it does | Exact commands | Extra prerequisites and limits |
|---|---|---|---|
| `scripts/verify-all.mjs` (the steps are data in `scripts/lib/verifyChain.mjs`) | The verification chain of a round, as it was always run by hand, **same steps, same order, same commands** (version check; backend tests; jar; extract; UI; desktop build; type check; frontend, desktop and NSIS-cleanup tests; the eleven real-shell suites; the layout suite on a scratch copy of the fictional sample school; packaged and hard-kill; backup-flow; the page count; the stale installer's size, time and SHA-256 before and after). Each step writes its own log to `desktop/test/out/verify-<date>-<time>/` (git-ignored); a failing step does not stop the chain; the exit code is 1 if any step failed. The NSIS-cleanup step is the one step added. | `node scripts/verify-all.mjs --list` (prints the steps and exact commands; runs nothing)  ·  `node scripts/verify-all.mjs` (about 20 minutes: 28 steps, rebuilds the jar, the extracted backend, the UI and the desktop build)  ·  `node scripts/verify-all.mjs --unpacked-build` (adds `node scripts/build-all.mjs --dir --skip-tests`, the UNPACKED app, as before 2026-11-06)  ·  **after the final build:** `node scripts/verify-all.mjs --no-rebuild`  ·  `--only a,b` / `--skip a,b` / `--out <folder>` / `--timeout-min <n>` | JDK 21 (found by `scripts/run-mvn.mjs`: `JAVA_HOME` or `%USERPROFILE%\.jdks\corretto-21.0.6`) and the Maven wrapper; no KPSMS.exe running; about 3 GB free. **The only things it deletes:** the two Eclipse-stub folders `backend/target/classes` and `backend/target/test-classes` (build output, git-ignored, rebuilt by the step; checked to be inside `backend/target`) and the scratch folder it makes for the layout suite (checked to be a `kpsms-layout-*` folder in the temp directory). A log folder that already holds files is refused. The real data folder `%LOCALAPPDATA%\RuralSchoolManagement` is never read or written; every suite uses its own temporary data folder. |
| `scripts/count-pages.mjs` (runs `scripts/lib/count-pages-electron.cjs` inside Electron) | Prints each handout to an A4 PDF with the program's own print engine (`printToPDF`) and counts the pages. Default: `docs/HANDOVER-KM.html` and `docs/SMARTSCREEN-KM.html`, each expected to be **1** page. | `npm run check:pages`  ·  `node scripts/count-pages.mjs <file.html> [<file.html> ...] [--expect <n>] [--keep <folder>]` | Writes only into a fresh temporary folder (removed at the end) or a new `--keep` folder, and never over an existing file. Exit 1 if any file has another number of pages or cannot be printed. |
Both are guarded by `desktop/test/verifyScripts.test.mjs` (in `npm run test:desktop`): the steps and their order are those of the hand-run chain, every script they run exists, **nothing in the chain installs, uninstalls or builds an installer** (the only build is the opt-in unpacked one), nothing destructive is in a command, the two deletions are guarded, and the options behave. **Not yet run:** `--unpacked-build` and `--no-rebuild` (only listed and unit-tested); the first real use of `--no-rebuild` is after the final build.
