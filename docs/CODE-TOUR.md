# Code tour — how the school system fits together

For the owner, to re-read before changing anything. Written from reading the code (2026-10-31); the "proven" column of
`PHASE1-PROGRESS.md` … `PHASE5-PROGRESS.md` says what has actually been run.

## 1. The picture
```
Electron (desktop/)  ──starts──▶  Java + Spring Boot (backend/)  ──reads/writes──▶  SQLite file (school.db)
   │  serves the UI at app://school                ▲ HTTP on 127.0.0.1:<random port>
   └──▶ Nuxt web pages (frontend/) ────────────────┘   (Bearer token + a per-launch secret header)
```
- Electron picks a random secret, starts the bundled Java with the secret and data folder in **environment variables**, and waits for the line
  `SMS_READY {"port":N}` on its stdout. If Electron dies, the backend notices its stdin closing and exits.
- The secret header is added by Electron's main process, so the web page's JavaScript never sees it. Other programs on the PC cannot call the API.
- Data lives in `%LOCALAPPDATA%\RuralSchoolManagement` (never in the install folder): `database/`, `uploads/`, `backups/`, `logs/`, `config/`.

## 3. Rules that are easy to break
- Spring is the **only** thing that touches SQLite. The web page never does.
- SQLite quirks that are handled on purpose: `transaction_mode=IMMEDIATE`; Flyway runs on its own connection with foreign keys OFF and asserts `foreign_key_check` after table rebuilds; the driver's default date mapping is wrong, so every date/time/boolean has an `AttributeConverter`.
- Logs, audit entries and diagnostics hold **codes and ids only** — never passwords, keys, tokens, or names (a test scans for this).
- Vue reactive objects cannot cross Electron IPC (`toPlainData()` in `services/desktop.ts`); the PDF margins are white because the window's base colour is white.
- A migration is never edited once written: V1, V2, V3 (Phase 2), V4 (Phase 3), V5 (Phase 4), V6 (sign-offs), V7 (attendance periods), V8 (sub-subjects), V9 (homework) and V10 (timetable) are final. New schema = `V11__...sql`. (Phase 5 needed none: the backup history is a file, not a table.)
- **Backups and restore**: a backup is made with `VACUUM INTO`, never by copying `school.db` (a WAL database copied while open is not consistent). Every zip is read defensively (entry names against a fixed pattern, sizes bounded while streaming, every hash compared, the database opened read-only and checked) because it may come from a USB stick. The backend never receives a path: the page sends an id or an `incoming-<n>.zip` name. A restore is **applied before the database opens** (`RestoreBootstrap`), never under a live connection pool. The history (`config/backup-history.json`) is outside the database so a restore cannot overwrite it; the zips are the truth and the history only adds facts. The last verified backup can never be deleted or rotated away. **A restore also restores that backup's password and recovery key** (they are in the database): the dialog says so.
- A backup copied to a USB stick counts as "elsewhere" only if the shell proved the copy by its SHA-256 **and** it is on a different drive letter than the data; the same drive is reported but not counted.
- Closing the window asks the page first (the exit prompt); if the page does not answer in 5 seconds the program closes anyway, so nobody is trapped behind a dead page.
- History hangs off the **enrollment**, not the student: a promotion or transfer closes one enrollment and opens another, so old records never change. Attendance and scores hang off the enrollment too, which is why a student with any of them cannot be deleted.
- Scores, maximums and weights are stored as whole hundredths (7.25 → 725); people may type at most two decimals. **An empty score is "not entered", which is not 0**; "absent" is its own flag and counts as 0 in the total.
- A closed academic year freezes attendance, examinations, scores, comments, homework and fee **charges** (reading still works). Fee **payments and voids still work** in a closed year: money owed does not disappear with it.
- **A grading scale is frozen per examination**: the first score entered records the scale in use (`examinations.grading_scale_id`). Editing a scale that an examination already uses makes a NEW scale (the old one is archived, kept for those examinations), so old results and report cards never change. A scale nothing was graded with is edited in place.
- A payment is never deleted: a mistake is voided with a reason, the receipt number stays on record and is never reused. A charge with any payment (even a voided one) cannot be deleted.
- Money is never a floating-point number: whole riel, or cents for dollars (`fees/Money`). The API speaks in ordinary units and refuses decimals the currency does not have.
- JDBC trap: `rs.wasNull()` refers to the column read **immediately before** it. Read the nullable column, call `wasNull()`, only then read the next one (this caused three bugs while writing Phase 3).
- Lists of people are sorted in the browser by Khmer name (`utils/sort.ts`); the server returns them in database order.
- Components are used by file name (`pathPrefix: false`): two components must never share a file name, even in different folders.
- **`release/release.json` is the only place the name and the version are typed.** Everything else is derived or checked by `node scripts/version.mjs check` (the build runs it first). The database schema number (the last migration) is a different number from the program version.
- **A developer can never mark something "accepted by the school".** `release/acceptance.json` may only say whether work is done and what is pending; "final school acceptance" is a row the administrator writes through the program (`acceptance_signoffs`). The build rejects a registry that claims it.
- **Attendance sessions are data, not an enum.** A sheet snapshots its session's name and times, a session with sheets is switched off and never deleted, the database refuses a student twice in one session and day, and the clock never decides what may be recorded. The counts (dashboard, history, report card) count sheets, not days: whether the school counts days or sessions is its decision.
- **The program stores nothing in the browser** (a shell test checks localStorage, sessionStorage and cookies): even "remember the last session" is kept in a Pinia store and is gone after a reload or a sign-out.
- Every new backend error code needs Khmer text in `km.json` (`frontend/tests/i18n.test.ts` fails otherwise); every new icon must be listed in `frontend/app/config/icons.json`.
